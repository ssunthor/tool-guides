# Legal Knowledge Ingestor (LKI) - Design Document

**Version:** 0.7.0
**Date:** 2026-05-14
**Category:** Ingestor (I)
**Acronym:** LKI

---

## 1. Introduction & Purpose
The Legal Knowledge Ingestor (LKI) is the semantic "Brain" of the Legal Knowledge Base suite. It bridges the gap between the raw Markdown generated by the Legal Document Parser (LDP) and the vector/relational databases queried by the Assistant (LKA).

Its primary goal is to intelligently chunk, summarize, and embed legal contracts, while resolving temporal lineage (e.g., Amendments overriding MSAs) to ensure RAG retrieval is highly accurate. Currently, the application is in heavy development with a primary focus on perfecting the advanced semantic chunking pipeline.

## 2. The Database Bridge
The LKI operates on the same PostgreSQL database (`legal_kb_db`) as the Parser. 
* **Source of Truth:** The LDP writes to `document_jobs` (UUID, markdown path, CMD group).
* **Ingestion Target:** The LKI reads `document_jobs` and writes to `legal_documents` (mapping `parser_job_id` -> `document_jobs.id`).

## 3. Categorization-Based Chunking (Strategy Pattern)
Because a 200-page Master Services Agreement cannot be chunked the same way as a 1-page email notice or a dense Excel pricebook, the LKI uses the `extracted_category` from the Parser to dictate the extraction strategy and guide the LLM's reasoning.

1. **Master Services Agreements (MSAs) & Amendments:**
   * *Strategy:* LLM Semantic Pointer Extraction. The LLM is instructed to look for rigid contract structures (Preambles, Recitals, Legal Clauses, Signature Blocks).
   * *Enrichment:* Heavy emphasis on HyDE (Hypothetical Document Embeddings) to map user questions (e.g., "What happens if we breach?") to legal clauses ("12.4 Material Breach").
2. **Schedules / Pricebooks:**
   * *Strategy:* Table-Centric Isolation.
   * *Enrichment:* Utilizes the `TableSummarizer` to convert pricing matrices and SLAs into natural language paragraphs so the Vector DB can accurately retrieve structured data.
3. **Notices & Correspondence:**
   * *Strategy:* Fast-Path Bypass (Metadata & General Text Extraction). The LLM is instructed to bypass complex legal hierarchies and focus on `correspondence_header` (TO, FROM, DATE) and `general_text` bodies to keep emails/letters intact.

## 4. Advanced Semantic Chunking Pipeline
To process complex documents without losing data or hallucinating text, the LKI utilizes a hybrid **LLM Reasoning + Python Deterministic** approach.

### 4.1 Phase 1: Intelligent Preprocessing & Artifact Scrubbing (`preprocessor.py`)
Before any chunking begins, the raw Markdown is sanitized to prevent OCR noise from interfering with clause boundaries:
* **Repeating Header/Footer Detection:** Calculates frequency distributions of lines at the top and bottom of pages. Artifacts appearing across multiple pages (e.g., "Confidential", page numbers) are scrubbed.
* **Signature Noise:** Strips massive base64 or HTML blocks related to DocuSign markers (`<signature>`, `<div>DS</div>`), storing the IDs in metadata.
* **Page Marker Preservation:** Physical page markers are removed from the visible text but tracked via a line-to-page mapping index so every final chunk knows exactly which physical page(s) it belongs to.

### 4.2 Phase 2: Context-Aware Pointer Extraction (`semantic_chunker.py`)
This phase relies on an LLM to understand the logical flow of the contract without actually rewriting the text.
* **Line Numbering:** Every line of the scrubbed Markdown is prepended with an index `[L0]`, `[L1]`, etc.
* **Context Injection:** The document's Category is injected into the prompt to set the correct extraction schema.
* **Sliding Windows:** The document is fed to the LLM (e.g., `gemma4-31b`) in overlapping batches (e.g., 400 lines with 100 lines of overlap).
* **Pointer Output:** The LLM returns a strict JSON array of pointers (`start_line`, `end_line`, `chunk_type`, `toc_number`).
* **Fallback Mechanisms:** If the primary "thinking" LLM fails to output valid JSON pointers after retries, the system automatically falls back to a faster, non-thinking model configuration to guarantee throughput.

### 4.3 Phase 3: Deterministic Structural Merging (The Safety Net) (`structural_merger.py`)
Because sliding windows create overlapping JSON outputs and LLMs occasionally make mistakes, the LKI utilizes a "Defense in Depth" deterministic merger to cleanly resolve boundaries before saving to the database.
* **Overlap Deduplication:** Overlapping pointers from the sliding windows are mathematically fused into continuous blocks.
* **Advanced Table Stitching & Classification:** HTML/Markdown tables are frequently split across page breaks. The merger scans adjoining table chunks. If column counts match, or if a fragment is separated only by a stray OCR artifact (< 60 words), the merger safely stitches the `<tr>`/`<td>` tags back together, recalculating the `end_idx` and `page` metadata. Utilizing logic prototyped in `test_table.py`, it also classifies tables as either "Layout" (to be flattened) or "Data" (to be preserved).
* **Boundary Sanitization:** Scans for and removes duplicated headers leaking across chunk boundaries (e.g., if "12. Liability" accidentally bled into the end of chunk 11 and the start of chunk 12).
* **Orphan Catching (Gap Stitching):** The script scans for small line gaps (1-5 lines) between chunks and forces the preceding chunk to expand and absorb the orphaned text or orphaned headers.

### 4.4 Phase 4: Dynamic TOC & Hierarchy Building (`toc_builder.py`)
If a contract lacks an explicit Table of Contents, the system builds a virtual one:
* **Stack-Based Resolution:** Analyzes the assigned `toc_number` of each chunk (e.g., "9.1.2").
* **Deterministic Parenting:** Pushes and pops hierarchy levels to figure out exactly where a clause fits, automatically generating `ancestor_titles_list` and prepending context to child chunks before they are embedded.

## 5. Temporal Lineage & Document Mapping
To solve the problem of RAG returning outdated terms from an MSA when an Amendment exists, the LKI maps document relationships:
1. **Grouping:** Documents are strictly grouped by their `cmd_client_group_id`.
2. **Chronology:** Documents within a group are sorted by `extracted_date`.
3. **Knowledge Graph Triplet Extraction:** During ingestion of Amendments, the LLM extracts triplets that define overrides (e.g., `[Amendment 1] -> MODIFIES_CLAUSE -> [MSA Section 4.2]`). 
4. **Vector Tagging:** Embeddings are tagged with a `temporal_weight` or `superseded_by` metadata flag to guide the Retriever (LCR) at search time.

---

## 6. Enrichment & Metadata Extraction
Following chunking, the pipeline triggers batch LLM prompts to enrich the database:
1. **The "140 Fields" Extraction:** Pre-computes answers for all required CMD metadata fields.
2. **Multi-Phase Summarization:** Generates standard brief/detailed summaries. For massive documents (>30k chars), uses a Map-Reduce pipeline (Rank -> Extract -> Synthesize -> Critique).
3. **Table Summarization:** Converts complex HTML pricing tables and SLAs into natural language paragraphs so the Vector DB can accurately retrieve structured data.
4. **HyDE Generation:** Generates synthetic questions (e.g., "What happens if we breach?") for specific legal clauses.
5. **Knowledge Graph Extraction:** Maps entity relationships via triplets (Subject -> Predicate -> Object).

## 7. CLI-Driven Development
The LKI is driven by a `click` CLI (`ldi_cli.py`) with specialized command groups to facilitate local development and bulk operations:
* **Pipeline Commands (`ingest`, `run-task`):** Executes the main processing workflow or standalone tasks.
* **Test Commands (`test-chunking`):** Allows rapid testing of the LLM Pointer extraction logic, outputting detailed analytics directly to JSON.
* **Audit Commands (`audit-chunks`, `inspect-backlog`):** Includes a local-only "LLM-as-a-Judge" QA tool to automatically evaluate chunking quality during development, preventing the need to manually review thousands of JSON files.

## 8. Continuous Learning & HITL RAG Feedback (Future Enhancement)
To prevent the RAG system from repeatedly failing on the same ambiguous queries, the LKI and Retriever (LCR) will implement a **Human-In-The-Loop (HITL) Self-Healing Loop**. 

Because vector similarity is not perfect, users interacting with the chatbot might receive an incomplete answer if the Retriever fetches the wrong chunk.

* **The Feedback Mechanism:** If an answer is inaccurate, the UI will allow the user to browse the document's chunks and manually flag the *correct* clause that should have been retrieved for their specific query.
* **The Learning Cache:** The system will save this interaction (the user's query vector + the correct `chunk_id`) in a dedicated PostgreSQL "Golden RAG Cache" scoped strictly to that specific CMD Client Group.
* **Self-Healing Retrieval:** In future sessions, when a new user asks a semantically similar question (evaluated via a high fuzzy/vector similarity threshold to the cached query), the Retriever will automatically force-inject the previously human-validated chunk into the LLM's context window. This creates a highly localized, customer-specific reinforcement learning loop without the massive computational expense of fine-tuning the base embedding model.
