## 1. Introduction & Purpose

The **Code Analyst (CA)** is a specialized AI-driven processor module within the SERA ecosystem. Its primary function is to deeply understand the source code of all modules within the ecosystem, enabling the automated generation of design documents, changelogs, and providing code intelligence to other services.

This module is designed to be the definitive source of truth for "what the code does," moving beyond unreliable human-written documentation or commit messages. By programmatically analyzing the source code itself, the CA provides a consistent, accurate, and always up-to-date understanding of every module's capabilities.

Furthermore, following the "Architect & Builder" methodology, the CA acts as the ecosystem's automated engineering team. It moves beyond simple "code completion" by utilizing a **bi-modal, multi-agent architecture** that separates high-level architectural reasoning from low-level syntax generation, ensuring that code is not just syntactically correct, but structurally sound and architecturally compliant.

The core outputs of the CA are:

-   **Automated Design Documentation:** The ability to generate a full `design.md` document for any module purely from its source code.
-   **Structured Changelogs (`changelog.json`):** A detailed report of changes between deployments, generated by comparing code analysis reports.
-   **Autonomous Feature Implementation:** A workflow where the CA accepts a feature request, plans the architecture, and writes the code to implement it.
-   **Code Intelligence API:** An API for other ecosystem modules to query for information about code, such as confirming the implementation of a feature request.

## 2. Architecture & Integration

**Service Type:** (P) Processor. The CA is a flexible tool that operates as a hybrid Local/Cloud service. It can be operated in three primary modes:
1.  **CLI-Driven:** A command-line tool designed for explicit execution, making it perfect for integration into a CI/CD pipeline, a deployment script (e.g., `deploy.sh`), or for manual feature implementation requests.
2.  **Watcher Mode:** A persistent background service that actively monitors specified project folders for file system changes, triggering analysis automatically.
3.  **Agent Mode:** Autonomous loop for generating new applications or features using the dual-agent workflow.

**The "Split-Brain" Model Strategy:**
To mitigate "spaghetti code" and hallucinations, the CA utilizes two distinct AI agents with specialized roles and models:

1.  **The Architect (Planner):**
    * **Role:** Reasoning, Planning, file-structure analysis, and spec generation. *Does not write code.*
    * **Model:** **Gemini 3 Pro** (accessed via `gemini-cli`).
    * **Capability:** High-context window, superior logic, and architectural foresight. It dictates *what* needs to be done.
2.  **The Builder (Coder):**
    * **Role:** Implementation, syntax generation, and file editing.
    * **Model:** **Gemma 3:27b** (hosted locally on SERA hardware).
    * **Capability:** High speed, low latency, fine-tuned for code completion and syntax correctness. It executes *how* it gets done based on the Architect's plan.

**Called by:**

-   **Deployment Scripts (`deploy.sh`):** In CLI-Driven mode, this is a primary trigger. The script calls the CA before and after code is updated to generate a change analysis.
-   **File System Events:** In Watcher Mode, the CA subscribes to file system notifications (create, modify, delete) within the target directories, triggering analysis autonomously in real-time.
-   **Other SERA Modules:** Services like the CAP can query the CA's API to get the latest changelog for a specific module to validate that a feature request has been implemented.
-   **Developer CLI:** Direct interaction for bootstrapping new modules or implementing specific features.

**Interacts with:**

-   **Shared Assets Storage (`/assets`):** The CA requires read access to the source code of all other modules. It writes its generated artifacts (snapshots, changelogs, updated docs, and implementation plans) to a dedicated directory within `/assets/ca/`.
-   **Local Inference Engine:** Hosts the Gemma 3 model for the Builder agent.
-   **Cloud Gateway:** Connects to the Gemini 3 Pro API for the Architect agent (AI Factory).

## 3. Core Functionality & Process Flow

The Code Analyst's primary task is to create a structured, semantic understanding of a codebase and use that understanding to generate new code. This is achieved through two distinct pipelines: The **Analysis Pipeline** (Reading/Understanding) and the **Generation Pipeline** (Writing/Creating).

### 3.1. The Analysis Pipeline (Reading)

This pipeline is run for each file that needs to be analyzed (for documentation and changelogs).

**Pass 1: Structural Parsing (Deterministic):** The CA first uses a language-specific, deterministic code parser (e.g., Python's `ast` module, a tree-sitter library for JavaScript/React) to create an Abstract Syntax Tree (AST) or "map" of the file. This is a non-AI step that builds a high-level outline, identifying:

-   The file's imports and dependencies.
-   All classes and their methods.
-   All standalone functions, their arguments, and return types.
-   Associated docstrings and comments.

**Pass 2: Granular Summarization (AI-Powered):** The CA then iterates through the structural map from Pass 1. For each individual function or class method, it sends only that small, isolated block of code to an LLM.

-   **Prompt:** "You are a senior developer writing technical documentation. Explain the purpose, inputs, and outputs of this single function in one sentence."
-   **Result:** This generates a collection of small, highly accurate summaries for every component of the file. This approach avoids context window limitations and allows the AI to focus on a single, well-defined task at a time.

**Pass 3: High-Level Synthesis (AI-Powered):** Finally, the CA aggregates all the individual summaries from Pass 2 and sends them to a more powerful reasoning LLM.

-   **Prompt:** "You are a technical architect creating a design document. Based on the following list of function and class summaries from a single file, write a high-level, one-paragraph summary of the entire file's purpose, primary capabilities, and its role within the application."
-   **Result:** The LLM synthesizes the granular details into a coherent, high-level understanding of the entire file, without ever needing to see all the source code at once.

The final output of this pipeline is a structured JSON object representing the "analysis" of a single file.

### 3.2. The Generation Pipeline (The "Architect & Builder" Workflow)

This pipeline allows the CA to write code autonomously. It strictly follows a **Spec-First** approach.

**Phase 1: The Architect (Plan Generation)**
-   **Input:** A user request (e.g., "Add JWT authentication to the user module") + The current file structure + `design.md`.
-   **Process:** The request is sent to **Gemini 3 Pro**. The Architect analyzes the request against the existing architecture.
-   **Output:** A structured `implementation_plan.md`. This plan contains:
    1.  List of files to create.
    2.  List of files to modify.
    3.  Step-by-step logic for each file (pseudo-code or high-level requirements).
    4.  *Crucially, no actual code is written here.*

**Phase 2: The Builder (Code Execution)**
-   **Input:** The `implementation_plan.md` from Phase 1.
-   **Process:** The CA iterates through the steps in the plan. For each step, the **Gemma 3:27b** local model is invoked with the specific instruction: "You are a Senior Developer. Read step #1 of this plan and implement it exactly. Do not deviate."
-   **Output:** Actual source code files written to the disk.

**Phase 3: Verification (The Loop)**
-   **Process:** Once the Builder finishes, the Architect (Gemini 3 Pro) scans the new files.
-   **Prompt:** "Compare the generated code against the original `implementation_plan.md`. Does it satisfy the requirements? If not, create a remediation plan."
-   **Result:** If approved, the cycle ends and the Analysis Pipeline is triggered to update docs. If rejected, the Builder is re-tasked.

### 3.3. Primary Workflows

The analysis and generation pipelines are used as building blocks for the CA's main features.

**Workflow 1: Generating a Changelog (Diff Analysis)**
This workflow is triggered via a `deploy.sh` script or an internal file system event in watch mode. It uses a "snapshot and compare" model.

1.  **Snapshot (`--snapshot`):** Before deployment or on initial watch, the CA is run to create a manifest of content hashes for all files in a module, representing the "before" state.
2.  **Analyze (`--analyze`):** After deployment or upon file change, the CA is run again. It identifies changed files by comparing new hashes to the snapshot. For each modified file, it runs the full analysis pipeline on both the old and new versions of the file.
3.  **Compare & Summarize:** The two analysis reports (before and after) are then sent to an LLM with the prompt: "Compare these two analysis summaries and describe the change in functionality." The result is a human-readable changelog entry.
4.  **Intelligent Pruning (Post-processing):** After a new changelog entry is generated, a post-processing step is initiated. The CA analyzes the history of the changed components. If a new change completely removes or fundamentally replaces a feature that was described in previous changelog entries (e.g., a feature is added, refactored, then removed entirely), those older entries are flagged as `"status": "obsolete"`. The LLM is prompted to trace the feature's lifecycle: "This latest change removes function 'X'. Review the provided changelog history for this function and mark all related entries (additions, modifications) as obsolete."

**Workflow 2: Generating Documentation from Scratch**
This workflow is triggered manually by a user running the CA with a command like `python cda_cli.py --generate-docs --module-path <path>`.

1.  **Full Analysis:** The CA runs the full analysis pipeline on every single file in the specified module.
2.  **Synthesize Documentation:** It then aggregates all the high-level file summaries from Pass 3 and sends them to the LLM with a final prompt: "You are an AI architect. Based on these summaries of all files in a project, generate a complete design.md document, including sections for Introduction, Architecture, and Core Components."

**Workflow 3: Autonomous Watch Mode**
This workflow enables the CA to operate continuously without an external trigger script.

1.  **Initialization:** The CA is started with the `--watch` command, pointing to a specific module path. It performs an initial full analysis of all files to establish a baseline snapshot and state.
2.  **Monitoring:** The service enters a persistent loop, using the operating system's file system notification services (e.g., inotify on Linux) to efficiently listen for events (file saves, creations, deletions, renames) in the target directory and its subdirectories.
3.  **Triggered Analysis:** Upon detecting a change on a specific file, the CA automatically triggers the "Diff Analysis" workflow (Workflow 1) for just that file, comparing the new version against its last known state. It then updates the `changelog.json` with the new entry and its pruning analysis, ensuring documentation is always in sync with the code.

**Workflow 4: Identifying Common Code for `sera_commons`**
This workflow transforms the CA into a proactive architectural tool, designed to help developers identify and consolidate duplicated code into a shared `sera_commons` library. It is triggered manually via a dedicated CLI command.

1.  **Full Ecosystem Scan & Fingerprinting:** The CA performs a deep scan of all modules in the ecosystem. Using its language-specific parsers, it deconstructs every file into individual functions and methods. For each code block, it generates a "structural fingerprint" that captures its signature and a normalized hash of its logic.
2.  **Candidate Clustering:** It compares all fingerprints across the entire codebase. Functions with identical fingerprints are flagged as direct duplicates. Functions with similar but non-identical fingerprints (e.g., a `setup_logging` function with minor variations in each service) are grouped into "candidate clusters."
3.  **Semantic Equivalence Analysis:** For each candidate cluster, the CA sends the code snippets to a reasoning LLM with a specialized prompt. The LLM's task is to determine if the functions are semantically equivalent despite their differences.
4.  **Refactoring Report Generation:** The final output is a markdown report (`refactoring_report.md`). The report details each cluster of duplicated code, provides the AI's analysis on their equivalence, and proposes a generalized, unified function signature suitable for inclusion in the `sera_commons` library. This provides developers with a clear, actionable list of opportunities to reduce code duplication and improve maintainability.

**Workflow 5: Autonomous Feature Implementation**
This workflow leverages the "Architect & Builder" separation to write code safely. Triggered via CLI: `python cda_cli.py --implement "Add rate limiting to API"`.

1.  **Context Gathering:** CA scans the project to build a context map.
2.  **Architectural Plan:** Gemini 3 Pro (Architect) generates `plans/rate_limiting_spec.md`.
3.  **Human Gate (Optional):** The system pauses for the user to review the markdown plan. If accepted:
4.  **Code Generation:** The Builder (Gemma 3) creates `middleware/rate_limiter.py` and updates `server.py` based on the spec.
5.  **Docs Update:** The Analysis Pipeline runs immediately to update `design.md` with the new feature.

**Workflow 6: New Module Bootstrap (App Creation)**
Triggered via CLI: `python cda_cli.py --bootstrap --name "inventory-service"`.

1.  **Architectural Definition:** Gemini 3 Pro is prompted to create a scaffolding plan for a standard SERA module (gRPC server, config, logging).
2.  **Scaffold Generation:** The Builder executes the plan, creating the folder structure and boilerplate files locally.
3.  **Commons Integration:** The Architect reviews the new files and suggests replacements from `sera_commons` to reduce duplication immediately.

## 4. Data Model & Storage

The CA relies on simple, file-based storage in the shared `/assets` directory.

**Snapshots (`/ai/assets/ca/snapshots/<module_name>/manifest_<timestamp>.json`):**
-   Stores the "before" state of a module.
-   **Structure:** A JSON object mapping relative file paths to their SHA256 content hashes.

**Changelogs (`/ai/assets/ca/changelogs/<module_name>/changelog_<timestamp>.json`):**
-   The primary output artifact for the diff analysis workflow.
-   **Structure:** A JSON object containing a list of change descriptions.

**Plans & Specs (`/ai/assets/ca/plans/<module_name>/<feature_request_id>.md`):**
-   Stores the implementation plans generated by the Architect. This allows for auditing "what was planned" vs "what was written" and facilitates the optional human review step.

### 5. API & Interface

### 5.1. Command-Line Interface (CLI)

This is the primary interface used by deployment scripts, developers, and for launching the background service.

-   `python cda_cli.py --snapshot --module-path <path_to_module>`: Creates the "before" state manifest for diffing.
-   `python cda_cli.py --analyze --module-path <path_to_module> [--update-docs]`: Generates a changelog by comparing to the latest snapshot and optionally updates the design document.
-   `python cda_cli.py --generate-docs --module-path <path_to_module>`: Generates a full design document from the current source code.
-   `python cda_cli.py --watch --module-path <path_to_module>`: Starts the CA in persistent Watcher Mode, actively monitoring the specified path for changes.
-   `python cda_cli.py --find-duplicates [--output-path <report.md>]`: Initiates the "Identifying Common Code" workflow across all configured modules and generates a detailed refactoring suggestion report.
-   `python cda_cli.py --implement "<feature description>" --module <path>`: Starts the Architect -> Builder loop for autonomous coding.
-   `python cda_cli.py --bootstrap --name <new_module_name>`: Creates a new application from scratch using the dual-agent flow.

### 5.2. gRPC / REST API

A simple, read-only API allows other modules to query the generated data.

-   `GetLatestChangelog(module_name: str) -> ChangelogResponse`: Returns the most recent `changelog.json` for a given module. This is how the CAP feedback service would confirm that a feature request was implemented.
-   `SubmitFeatureRequest(module: str, request: str)`: Remote trigger for the feature implementation workflow.

## 6. Configuration (`config/settings.yaml`)

-   `module_scan_paths`: A list of root directories for all SERA modules it needs to be aware of.
-   `file_exclusions`: A list of patterns to ignore during scanning (e.g., `__pycache__/`, `*.log`).
-   `storage_paths`: Base paths for storing snapshots and changelogs in `/assets`.

**Agent Configuration:**
```yaml
agents:
  architect:
    role: "planner"
    provider: "google_cloud"
    model: "gemini-3-pro" # The "Heavy Lifter"
    system_prompt: "You are a Senior Software Architect. Do NOT write code. Create detailed implementation specs."

  builder:
    role: "coder"
    provider: "local_inference"
    model: "gemma-3-27b" # The "Local Specialist"
    base_url: "http://localhost:11434"
    system_prompt: "You are a Senior Developer. Implement the code exactly as specified in the provided plan."

workflow_settings:
  require_human_approval: true # Pauses after the Architect phase for user sign-off
  auto_update_docs: true # Re-runs analysis after coding is complete
```

## 7. Future Enhancements

-   **Database Backend:** For larger-scale ecosystems, the file-based manifest could be replaced with a PostgreSQL database to track file versions, deployments, and changes over time, enabling more complex historical analysis.
-   **Automated Code Review Suggestions:** The AI analysis of code diffs could be extended to identify potential bugs, suggest performance improvements, or check for adherence to coding standards.
-   **Dependency Analysis:** The CA could be enhanced to parse dependency files (`requirements.txt`, `package.json`) and automatically flag any added, removed, or updated libraries in the changelog.
-   **Automated Test Generation:** As a highly advanced feature, the CA could analyze a change in a function and attempt to generate a new unit test case to cover the modification.
-   **Self-Healing:** If a build fails or an error is detected in logs, the CA automatically triggers a "Bug Fix" workflow where the Architect diagnoses the error log and instructs the Builder on the fix.

## 8. User Interface & Admin Suite Integration

While the Code Analyst (CA) is designed for programmatic use via its CLI and gRPC API, it will also feature a dedicated user interface to allow for interactive use, configuration, and review of its generated artifacts.

### 8.1. Standalone React UI

Following the architectural pattern established by other advanced modules like the CV Analysis Processor (CAP), the CA will be developed as a self-contained application that includes its own modern user interface.

* **Technology Stack:** The UI will be a Single Page Application (SPA) built with **React**, Vite, and Material UI.
* **Backend Service:** The existing core logic will be exposed via a **FastAPI** backend, which will serve both the static React assets and the RESTful API that the UI consumes.
* **Deployment:** The entire CA application (FastAPI backend + React frontend) will be a single, containerized service. In production, it will be accessible through the **Sera AI Gateway**, which will route traffic to its dedicated endpoint (e.g., `https://sera-ai.gt-t.net/ca/`).

### 8.2. Integration with the SERA Admin Suite

The development of a standalone UI for the CA directly informs the architectural strategy for the future **SERA Admin Suite**. The Admin Suite will not be a monolithic frontend; rather, it will act as a centralized portal or "aggregator shell."

When a user navigates to the "Code Analysis" section of the Admin Suite, the suite will simply load the CA's self-contained UI, likely within an iframe or a dedicated view. This ensures:
* **Single Source of Truth:** Any updates to the CA's user interface are made directly within the CA module's codebase and are immediately reflected in the Admin Suite.
* **Modularity:** The Admin Suite remains a lightweight orchestrator of administrative tools, not a bottleneck for their development.
* **Independent Development:** The CA can be developed, tested, and iterated upon as a complete, standalone product.
